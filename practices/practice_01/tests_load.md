# Нагрузочные проверки

## Что уточнили после Практики 2

Первая версия плана содержала учебные числа `20 RPS` и `p95 < 300 мс`, но для них не было подтверждённого источника. В `context.md` прямо указано, что production-лимит diff, модель, квоты и SLA пока неизвестны. Поэтому после шести экспериментов Практики 2 план разделён на:

1. **детерминированные проверки нашей API-обвязки с fake LLM** — их можно повторять локально и в CI;
2. **проверки защитных ограничений** — выполняются только для реально настроенных лимитов;
3. **provider load-test** — откладывается до выбора модели, квот и SLA и не подменяется выдуманными числами.

## Тестовый стенд

- HTTP endpoint: `POST /api/reviews`.
- Для основных нагрузочных сценариев используется fake LLM, чтобы задержка и ошибки внешнего провайдера не смешивались с производительностью API-обвязки.
- Fake LLM должен уметь:
  - отвечать сразу;
  - отвечать с заданной задержкой;
  - считать число вызовов;
  - по запросу бросать контролируемое исключение.
- Один и тот же тестовый diff используется во всех сравниваемых прогонах.
- Перед сравнением результатов фиксируются версия кода, параметры машины и параметры fake LLM.

## Сценарии

| ID | Цель | Нагрузка | Что измеряем | Критерий / ожидаемый результат | Источник |
|---|---|---|---|---|---|
| L-01 | Получить baseline API-обвязки | 100 последовательных валидных запросов, fake LLM без задержки | p50/p95 latency, error rate, CPU/RAM | 100% запросов завершаются контролируемым 2xx; p50/p95 сохраняются как baseline, но не объявляются production SLA | `tests_integration.md`, I-05; `context.md` |
| L-02 | Проверить поведение при росте конкуренции | одинаковая серия при 1, 5, 10 и 20 одновременных клиентах, fake LLM без задержки | p95, throughput, error rate, CPU/RAM | нет падения процесса и необработанных 5xx; изменение p95 и ресурсов фиксируется относительно L-01. Рост более чем в 3 раза — учебный сигнал для разбора, а не production SLA | результаты L-01; ограничение области из `context.md` |
| L-03 | Проверить отсечение слишком большого diff до LLM | 30 запросов размером `MAX_DIFF_BYTES + 1` после появления настроенного лимита | HTTP status, число вызовов fake LLM | 100% запросов отклонены контролируемым 4xx; `llm_calls = 0` | `adr.md`: нужна явная input validation; `context.md`: максимальный размер пока неизвестен |
| L-04 | Проверить поведение при медленной внешней зависимости | fake LLM с фиксированной задержкой; число параллельных запросов увеличивается ступенями | active requests, timeout/error rate, memory, время ответа | процесс не падает и ошибка остаётся контролируемой. Если в системе появится `MAX_IN_FLIGHT`/очередь, отдельный прогон выполняется на `limit + 1`; пока лимита нет, результат считается наблюдением, а не выполненным requirement | `tests_integration.md`, I-02; `adr.md` |
| L-05 | Проверить реального LLM-провайдера | только после выбора модели и получения квот/SLA | provider latency, 429/5xx, стоимость/токены, retry | критерии берутся из подтверждённых квот и SLA конкретного провайдера; до этого сценарий имеет статус **blocked** | `context.md`, раздел «Что пока неизвестно» |

## Порядок выполнения

1. Запустить L-01 и сохранить baseline.
2. Выполнить L-02 на той же машине и с тем же fake LLM; сравнивать только с baseline текущего прогона.
3. L-03 запускать только после появления фактического `MAX_DIFF_BYTES`; если лимит ещё не определён, тест не выдумывает его и помечается `blocked`.
4. L-04 выполнять с искусственной задержкой fake LLM. Не делать выводы о реальном провайдере по этому сценарию.
5. L-05 разблокировать после того, как известны модель, квоты и SLA.

## Что сохраняем как результат

Для каждого прогона сохраняются:

- версия кода/commit;
- конфигурация нагрузки;
- параметры fake LLM или имя реального провайдера;
- p50/p95, throughput и error rate;
- CPU/RAM;
- количество вызовов LLM там, где проверяется раннее отклонение;
- вывод `pass / fail / blocked` и причина.

## Границы выводов

- Результаты с fake LLM характеризуют нашу API-обвязку, но не производительность конкретной модели.
- Значение `20` конкурентных клиентов и коэффициент `3x` в L-02 — **учебные параметры эксперимента**, а не заявленный production SLA.
- Нельзя утверждать production RPS, максимальный diff или допустимый provider latency, пока эти требования не подтверждены отдельным источником.
- Если защитный лимит ещё не реализован, соответствующий сценарий должен быть `blocked`, а не «успешно пройден» на придуманном значении.

## Как использовали AI

- Базовая версия: `P1-11` в [`prompts.md`](prompts.md).
- Доработка в Практике 2: шесть экспериментов из [`../practice_02/prompts.md`](../practice_02/prompts.md) — Few-shot, R.C.T.F., Chain of Verification, Tree of Thoughts, RAG и ReAct.
- Инструмент / модель: **gpt-5.6 Sol**.
- Главное исправление после проверки: убраны неподтверждённые production-пороги; добавлены baseline, статусы `blocked`, трассировка источников и раздельная проверка API-обвязки и внешнего провайдера.
