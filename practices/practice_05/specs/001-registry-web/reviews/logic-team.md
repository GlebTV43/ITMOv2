# Независимая сверка команды логики

Дата: 2026-10-30. Этап: после решения пользователя по контракту, до кода.
Участник: отдельный агент `logic_team`; обмен решениями с `ui_team`.

## Проверено

- `logic.before.md`, `logic.spec.md`, `ui.spec.md`, `contract.md`.
- Публичные методы `Registry` практики 4 и тесты `test_registry.py`,
  `test_feature_a.py`, `test_unsubscribe.py`.

Registry уже задаёт trim, порядок проверки, границу 80/81 Unicode-символов,
идемпотентные bool-результаты и независимый отсортированный снимок.
Предлагаемый HTTP-адаптер совместим с этим поведением; менять Registry не нужно.
Блокирующих противоречий между согласованным контрактом и кодом не найдено.

## Что согласовано с UI

| Вопрос исходной спеки | Решение до реализации |
|---|---|
| Как передавать данные | UTF-8 form-urlencoded, ровно одно поле name |
| Где нормализовать | Только Registry; UI передаёт исходный текст |
| Что означает False | Нормальный исход, один из четырёх результатов через 303 |
| Что показывать при ошибке имени | 400, русское сообщение и исходное значение |
| Что показывать при сломанной форме | 400, пустое поле, состояние без изменения |
| Где хранится список | Один Registry на сервер, в памяти до завершения процесса |
| Как отписывать | Hidden name содержит точное имя с HTML-экранированием |

UI подтвердил отсутствие `maxlength=80`: оно ошибочно запрещало бы допустимое
имя из 80 символов с пробелами вокруг. Результаты отображаются по фиксированным
кодам; произвольный query-параметр не становится сообщением.

## Технические риски для плана и проверок

1. `parse_qs` по умолчанию игнорирует пустые значения и заменяет неверный
   Unicode. Для контракта нужны `keep_blank_values=True`, строгая декодировка
   и явная проверка набора/числа полей. Проверить missing, duplicate, extra,
   empty и invalid UTF-8 отдельно.
2. Лимит тела измеряется в байтах, длина имени — в символах после strip.
   Не смешивать эти ограничения; проверить кириллицу и 80/81 символ.
3. До чтения проверить Content-Length: не читать отрицательную/неограниченную
   длину. Не поддерживать chunked как альтернативный неограниченный путь.
4. BaseHTTPRequestHandler.path включает query. Маршрутизация использует
   разобранный путь; query результатов читается отдельно.
5. Экранировать имя и в тексте списка, и в атрибуте hidden input с кавычками.
   Проверить имя с `<`, `>`, `&`, одиночными и двойными кавычками.
6. Сохранить однопоточный HTTPServer и локальный bind. Каждый новый сервер
   получает новый Registry, чтобы тесты и перезапуск не разделяли состояние.
7. Сквозной HTTP-тест проверяет фактический 303, Location, следующий GET и
   сохранение списка при ошибке, а не только прямой вызов Python-функции.

Источники для поведения стандартной библиотеки:
[urllib.parse](https://docs.python.org/3/library/urllib.parse.html),
[http.server](https://docs.python.org/3/library/http.server.html).

Это проверка спецификации, а не утверждение о прохождении тестов ещё
не реализованной панели. Исходные before-файлы сохранены без изменений.

## Независимая проверка реализации

Проверены `lab/web.py`, `lab/view.py`, `lab/tests/test_http.py`,
`lab/scripts/check.py` против общего контракта и уточнённой логической спеки.
Код ревьюер не менял.

### Подтверждено чтением и отдельными запросами

- Registry загружается из файла практики 4, не скопирован; сервер создаёт
  отдельный экземпляр и слушает только 127.0.0.1.
- 80/81 проверяется существующим Registry после strip; адаптер не меняет
  нормализацию. Некорректные формы отвергаются до вызова операции.
- Разбор не теряет пустое значение; неверный UTF-8/percent encoding,
  повторяющиеся и лишние поля отклоняются. Сообщения результата — whitelist.
- HTML-значения и текст экранируются; ответы UTF-8 с байтовым Content-Length.
- Дополнительный независимый raw-HTTP probe: 11 сценариев PASS — missing и
  duplicate Content-Length, Transfer-Encoding, короткое тело, огромный числовой
  Content-Length, допустимая длина с ведущими нулями, пять неверных форм
  отписки. После ошибок реестр сохранял `A`.

### Обнаруженный дефект L-1: нестабильная доставка 413

Независимый запуск всех 25 HTTP-тестов: 24 PASS, ошибка в
`test_oversized_body_returns_413_without_mutation`.
Клиент получил `ConnectionAbortedError [WinError 10053]` вместо HTTP 413.
Повтор того же теста 20 раз: 17 PASS, 3 ошибки с тем же traceback при
`HTTPConnection.getresponse()`.

Причина по коду: ранний ответ на тело 4097 байт отправляется до его чтения;
затем HTTP/1.0 закрывает соединение с непрочитанными данными. Наблюдение
совместимо со сбросом TCP-соединения на Windows; это объяснение требует
подтверждения исправлением, а не ослаблением теста.

Ожидание по контракту: 413 и неизменный список должны доходить до клиента.
Нужна ограниченная по времени/объёму обработка непрочитанного тела при
закрытии отклонённого запроса, без неограниченного чтения входа.
Дефект передан основному агенту для исправления; до перепроверки L-1
реализация логикой полностью не принята.

### Перепроверка L-1 после исправления

Основной агент добавил `finish_rejected_request()`: после раннего ответа
выполняется flush и half-close отправки, затем ограниченное отбрасывание
непрочитанных данных (до 65536 байт, тайм-аут отдельного чтения 50 мс).
Отброшенное тело не разбирается и не передаётся Registry; исходный лимит
допустимой формы остаётся 4096 байт.

Независимый запуск на Windows после чтения исправления:

- 30 повторов `test_oversized_body_returns_413_without_mutation`: 30 PASS,
  0 ошибок соединения.
- Те же 11 дополнительных raw-HTTP сценариев: PASS, состояние сохранено.
- Весь HTTP-набор: 25 тестов PASS, 0 ошибок.

Итог: L-1 закрыт по фактической перепроверке. Блокирующих несоответствий
логической спецификации и общему контракту в проверенном объёме не осталось.
Ревьюер не менял код реализации или тестов. Браузерная проверка UI и финальная
приёмка пользователем остаются отдельными действиями.
