# Feature Specification: Веб-панель реестра подписчиков

**Feature Branch**: `practice_05`

**Created**: 2026-10-30

**Status**: Implemented and verified; awaiting user acceptance

**Input**: Продолжить проект практики 4; добавить согласованную веб-панель
по ДЗ5 «Две команды — одна фича» с другим SDD-фреймворком.

## User Scenarios & Testing

### User Story 1 - Просмотреть список и подписать имя (Priority: P1)

Пользователь видит подписчиков и добавляет имя через форму.

**Why this priority**: минимальная полезная панель существующего реестра.

**Independent Test**: открыть пустой список, добавить имя и увидеть одну запись.

**Acceptance Scenarios**:

1. **Given** пустой реестр, **When** открыта панель, **Then** видны пустое
   состояние и подписанная форма добавления.
2. **Given** `  Анна  `, **When** отправлена форма, **Then** показана `Анна`
   и сообщение об успешном добавлении.
3. **Given** существующее имя, **When** повторена подписка,
   **Then** показано «Уже подписан», дубль отсутствует.

### User Story 2 - Отписать выбранное имя (Priority: P2)

Пользователь удаляет подписчика кнопкой его строки.

**Why this priority**: завершает управление существующими подписками.

**Independent Test**: подготовить два имени, удалить одно и увидеть второе.

**Acceptance Scenarios**:

1. **Given** два подписчика, **When** отписано выбранное имя, **Then** только
   оно исчезает и показано «Подписчик удалён».
2. **Given** отсутствующее имя, **When** повторена отписка, **Then** показано
   «Подписчик не найден», остальные записи не меняются.

### User Story 3 - Исправить ошибку без потери данных (Priority: P1)

Пользователь получает понятную ошибку и может исправить ввод.

**Why this priority**: сохраняет правила и данные исходного проекта.

**Independent Test**: отправить пустое и слишком длинное имя, сверить список.

**Acceptance Scenarios**:

1. **Given** непустой список, **When** отправлено пустое или длиннее 80
   символов после strip имя, **Then** показана ошибка, ввод сохранён,
   список не меняется.
2. **Given** 80 Unicode-символов, **When** добавлено имя, **Then** оно принято.
3. **Given** HTML-разметка в имени, **When** открыта панель, **Then** имя
   отображается текстом и не исполняется как HTML.

### Edge Cases

Пробелы вокруг имени; дубль после нормализации; отсутствующее имя при отписке;
80/81 Unicode-символ; неверная форма; слишком большое тело; обновление
после действия; независимое состояние нового сервера.

## Requirements

### Functional Requirements

- **FR-001**: Панель MUST показывать отсортированный список или пустое состояние.
- **FR-002**: Подписка MUST сохранять нормализацию, правила длины и идемпотентность.
- **FR-003**: Отписка MUST удалять только выбранное имя; отсутствие не ошибка.
- **FR-004**: Ошибка MUST быть понятна пользователю и не менять список.
- **FR-005**: Имена MUST отображаться как текст в списке и полях форм.
- **FR-006**: Обновление после успешного действия MUST не повторять отправку формы.
- **FR-007**: Состояние MUST жить только до завершения процесса сервера.
- **FR-008**: Старое поведение Registry MUST сохраняться полностью.
- **FR-009**: Некорректные запросы MUST отклоняться по общему контракту до изменения данных.

### Key Entities

- **Подписчик**: уникальное нормализованное имя длиной 1–80 Unicode-символов.
- **Результат**: добавлено, уже подписан, удалено, не найдено либо ошибка.

## Success Criteria

### Measurable Outcomes

- **SC-001**: В браузере выполнен цикл открыть -> подписать -> отписать.
- **SC-002**: Все пять условий приёмки общего контракта подтверждены проверками.
- **SC-003**: Дубль и обе границы длины дают ожидаемый результат без потери чужих записей.
- **SC-004**: Все 56 существующих регрессионных тестов проходят.
